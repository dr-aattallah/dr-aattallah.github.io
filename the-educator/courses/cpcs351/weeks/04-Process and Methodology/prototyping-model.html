Prototyping Model

Instead of freezing uncertain requirements and hoping they are correct, the team builds a throwaway working model, lets users experience it, and uses the feedback to discover what the real system should be.

“Do not argue for weeks about an unclear screen. Build a small version, put it in front of users, and learn from what they actually do.”

Why Prototype?

The model attacks uncertainty directly

👥
Active User Involvement

Users participate in shaping the system rather than waiting until late testing.

💡
Better Understanding

A working model makes abstract requirements concrete and easier to discuss.

🔎
Earlier Errors

Misunderstood requirements and interface problems can appear before full implementation.

⚡
Fast Feedback

Missing functionality and better alternatives can be discovered quickly.

Worked Example · Step by Step

Prototype a University Registration System

Suppose students complain that registration is confusing, but they cannot agree on what a better experience should look like. That is a good prototyping problem.

01
LISTEN

Collect the currently known requirements

Interview students, advisors, and registration staff. Do not pretend the requirements are complete. Capture the parts everyone agrees on and explicitly mark uncertainty.

Search sectionsAdd/dropPrerequisitesSchedule conflictUnknown: best UI flow
OUTPUTInitial Requirement SetEnough knowledge to build a focused prototype—not enough to freeze the final system.
02
SELECT

Choose what uncertainty the prototype should explore

Do not prototype everything. Here, the biggest uncertainty is the student's add-course workflow: searching, seeing prerequisite status, avoiding conflicts, and understanding failures.

Target high-uncertainty workflowIgnore unrelated admin features
OUTPUTPrototype ScopeStudent search + section details + add-course feedback.
03
BUILD

Build a quick working prototype

Create only enough behavior for users to experience the interaction. A dummy course list and simulated prerequisite responses are acceptable because the goal is learning, not production reliability.

Clickable screensDummy dataSimple validationFast construction
OUTPUTPrototype v1Looks and behaves enough like registration to trigger meaningful user reactions.
04
REVIEW

Put the prototype in front of users

Ask students to complete realistic tasks rather than simply asking whether they “like” the interface. Observe where they hesitate, misinterpret labels, or expect missing behavior.

Task: find CPCS 351Task: add sectionObserve errorsCollect comments
DISCOVERYUnexpected NeedStudents want conflict and prerequisite warnings before pressing “Add,” not after failure.
05
REVISE

Revise the prototype and requirements

Change the interaction so every section shows a readiness status: Eligible, Missing Prerequisite, Time Conflict, or Full. Then test the revised prototype with users again.

Revise UIAdd missing behaviorClarify terminologyRepeat review
OUTPUTPrototype v2 + Better RequirementsThe team now understands behavior that was not obvious in the first interview.
06
DISCARD

Freeze the learning—not the prototype code

Once the important requirements are understood, document them properly and engineer the production system using appropriate architecture, security, performance, database, testing, and maintainability practices.

Update SRSRecord decisionsDiscard shortcutsDesign production solution

Throwaway Means Throwaway

Do not confuse the learning model with the production system

Prototype

Fast, incomplete, possibly inefficient, using dummy data or shortcuts. Optimized for learning and feedback.

🗑discard shortcuts

Production System

Engineered for correctness, security, performance, reliability, maintainability, integration, and long-term operation.

Strengths vs Limitations

Rapid learning has its own risks

✓ Advantages

✓Users are actively involved in development.
✓A working model improves users' understanding of the system being developed.
✓Errors can be detected earlier.
✓Quicker user feedback can lead to better solutions.
✓Missing functionality can be identified more easily.

⚠ Disadvantages

!Can encourage an “implement then repair” style instead of disciplined analysis.
!Scope may expand beyond the original plan as users continuously request more.
!Users may mistake the incomplete prototype for the finished system.
!Fast prototyping can hide incomplete or inadequate problem analysis.

Mentor Insight

A successful throwaway prototype is allowed to be technically ugly if it creates valuable knowledge quickly. The mistake is allowing prototype shortcuts to silently become production architecture.

Key Takeaway

In the Prototyping Model, requirements are not frozen too early. A throwaway prototype is built from currently known requirements, reviewed by users, and revised to improve understanding. The learning is retained; the prototype itself does not have to become the final system.

Think Like a Software Engineer

Your prototype works and users love it. Why might rewriting it still be the correct engineering decision?

Ask what shortcuts were taken in architecture, security, performance, reliability, data integrity, testing, and maintainability. A successful learning model is not automatically a safe production system.
