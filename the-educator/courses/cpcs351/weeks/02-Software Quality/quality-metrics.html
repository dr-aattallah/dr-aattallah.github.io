Quality Measurements & Metrics

Software quality becomes easier to manage when we move from impressions to evidence. Measurements and metrics give engineers objective ways to observe software attributes.

“If quality is important, we need evidence. Metrics turn software characteristics into something we can observe, compare, and discuss.”

Original Lecture Definitions

Measurement is evidence

The lecture distinguishes measurement from metrics and then specializes the idea toward software quality.

Software Measurement

An objective, quantitative assessment of a software attribute.

Software Quality Metric

A standard measurement used to assess software quality.

Requirements Metrics

Measure the quality of what we ask for

The lecture explicitly names four requirements-quality properties.

Un-ambiguityCan the requirement be interpreted in only one clear way?
CompletenessDoes the requirements set include everything necessary?
CorrectnessDoes it accurately represent the intended need or rule?
ConsistencyDo requirements avoid contradicting one another?
Design Metrics

Measure structure before it becomes expensive

The original lecture lists the following design metrics and definitions.

Fan-In
The number of modules that call a given module.
Fan-Out
The number of modules called by a given module.
Cohesion
The relevance of the functions in a module to the module's core functionality.
Coupling
Data dependencies among modules.
Modularity
High cohesion and low coupling lead to high modularity.
Module Design Complexity
Integration tests required to integrate a module with its subordinate modules.
Design Complexity
Number of subtrees in structure charts with module M as a root.
Implementation Metrics

Measure the code we actually produce

Defects / KLOC

Defects normalized per thousand lines of code.

Documentation / KLOC

Pages of documentation per thousand lines of code.

Comment Lines / LOC

Relationship between comment lines and source lines of code.

Cyclomatic Complexity

Number of independent control-flow paths in a function, as referenced to McCabe (1979).

Object-Oriented Quality Metrics

Measure the class structure

Weighted Methods per ClassMetric related to methods contained in a class.
Depth of Inheritance TreeHow deep a class sits within an inheritance hierarchy.
Number of ChildrenHow many immediate subclasses inherit from a class.
Coupling Between Object ClassesDependencies and connections among object classes.
Response for a ClassMetric concerned with the response set associated with a class.
Lack of Cohesion in MethodsMetric concerned with how closely related a class's methods are.
Example 1 · University Registration System

Metrics across one familiar system

Requirements side

The team interviews students, advisors, and the registrar. Suppose the SRS contains many “shall” statements but several contradict each other about prerequisites.

A high number of requirements does not prove high quality. Consistency and correctness still matter.

Implementation side

The registration service has 8 defects in 4 KLOC. Another service has 4 defects in 1 KLOC.

Service A: 2 defects/KLOC. Service B: 4 defects/KLOC. Normalizing by size changes the comparison.
Example 2 · Design Quality

Why coupling and cohesion matter

High cohesion

A RegistrationService handles registration-specific responsibilities: checking prerequisites, validating capacity, and creating enrollment.

Its responsibilities are closely related to one core purpose.

High coupling

The same service directly depends on payment, messaging, reporting, identity, scheduling, and five unrelated database modules.

Changes in many other modules can now affect RegistrationService. Modularity becomes weaker.
Illustrated Story

The team that said “quality looks good”

Panel 1

Everything feels fine

The team says the system “looks clean” and “seems reliable,” but nobody has agreed on measurable evidence.

Panel 2

Ask what can be measured

They identify requirement consistency, fan-out, defects/KLOC, cyclomatic complexity, and class coupling.

Panel 3

Evidence appears

One module has unusually high fan-out and complexity. Another has twice the defect density of the rest.

Panel 4

Quality becomes discussable

The team now has evidence to investigate, compare, and improve—not just opinions.

Mentor Insight

A metric is evidence, not a verdict. A large number can signal a problem, but engineers still need context to interpret why it matters and what action—if any—should follow.

Key Takeaway

Software measurements are objective quantitative assessments of attributes. Metrics are standard measurements. The lecture organizes quality metrics across requirements, design, implementation, system, and object-oriented software, with specific measures such as requirement consistency, fan-in/fan-out, cohesion, coupling, defects/KLOC, cyclomatic complexity, inheritance depth, and class coupling.

Think Like a Software Engineer

A module has 0 defects reported. Does that prove it has high quality?

Consider whether it was tested enough, how complex it is, how maintainable it is, whether users exercise it, and what other metrics would be needed before drawing a conclusion.
