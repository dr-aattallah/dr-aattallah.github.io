Verification vs. Validation

Software can perfectly match its specification and still fail its users. Verification and validation protect us from two different kinds of wrong.

“Verification asks whether our engineering work matches the specification. Validation asks whether the specification and product match the real world.”

Original Lecture · Verification

Are we building the product right?

Verification checks that an implementation conforms to its specification. The lecture also emphasizes an abstraction relationship: a lower-level abstraction implements a higher-level abstraction.

Higher-Level AbstractionRequirements specification: what the design must satisfy.
→
Lower-Level AbstractionSoftware design: the implementation of the requirements at a more detailed level.

Design verification: check whether the software design satisfies the requirements specification. The same idea continues as design is implemented by code.

Original Lecture · Validation

Are we building the right product?

Validation checks the correspondence between a model and the real world. For example, a functional specification must correspond to the customer's real needs. The lecture describes validation as a process that seeks to refute a model, and identifies functional testing as a validation technique.

Static vs. Dynamic V&V

Do we need to execute the software?

Static Verification

Review, walkthrough, and inspection analyze a static system representation to detect problems. The product does not need to execute.

Review · Walkthrough · Inspection · Desk Checking

Dynamic Verification

Testing executes the product and observes its behavior. We judge what happens while the software is running.

Execute → Observe → Compare
Static Verification Details

Inspection, walkthrough, and desk checking

The original slides distinguish these activities rather than treating every review as the same thing.

Walkthrough
  • The developer reads through the program aloud.
  • Simple test data may be used.
  • The team is led through a manual simulation.
  • The product is checked step by step while being read aloud.
  • Other team members ask questions and stimulate doubts.
  • The developer explains and justifies answers.
  • Relatively informal.
Inspection
  • Uses a list of criteria: common errors, standards, and consistency rules.
  • The team checks for common errors and compliance with standards.
  • Does not require program execution.
  • Can be applied to requirements, design, code, test data, and other representations.
  • Effective for error detection.
  • Program inspection detects defects; it is not itself the defect-correction activity.
Desk checking: code reading performed by a single person. The slide characterizes it as informal and less effective than walkthrough or inspection.

Program inspection can reveal: logical errors, anomalies such as an uninitialized variable, and non-compliance with standards.
Peer Review

A structured conversation among peers

The product is reviewed by peers using review questions designed to assess it. Review results can vary because reviewers differ in knowledge, experience, background, and criticality. A meeting is usually conducted to discuss the results.

STEP 1OverviewPresent the product and assign products to reviewers.
STEP 2Independent ReviewReviewers evaluate the product and answer the review questions independently.
STEP 3Review MeetingReviewers present comments; the developer answers questions and clarifies doubts.
STEP 4Fix & SummarizeThe developer fixes problems and produces a summary of solutions; reviewers check changes.
STEP 5Review Again?A second review meeting may be needed.

Visual Summary from the Lecture

Developer point of view vs. customer point of view

The final V&V visual in the lecture adds a useful perspective distinction.

Verification

  • Verify intermediary products such as requirement documents, design documents, ER diagrams, test plans, and traceability matrices.
  • Developer point of view.
  • May be verified without executing software code.
  • Techniques shown: informal review, inspection, walkthrough, technical review, and peer review.

Validation

  • Validate the final end product such as developed software, service, or system.
  • Customer point of view.
  • Validated by executing the software code.
  • Techniques shown include functional testing, system testing, smoke testing, regression testing, and more.
Example 1 · University Registration System

Correct implementation, wrong need

Verification succeeds

The specification says: “A student may register only if the prerequisite course was completed in a previous semester.” The developers implement exactly that rule. Design and code match the specification.

✓ Building the product right.

Validation fails

The university actually allows a prerequisite to be taken concurrently with special approval. The specification missed a real business rule, so the perfectly implemented system rejects valid registrations.

✕ Not building the right product for the real university policy.
Example 2 · Mobile Banking

Two different questions, two different failures

Verification problem

The requirement says a transfer confirmation must display the transaction reference. The released screen omits it. The implementation does not conform to the specification.

Verification defect.

Validation problem

The screen displays the reference exactly as specified, but customers cannot recognize which beneficiary received the money because the beneficiary name was never included in the requirement.

The specification itself did not capture the real user need.

The lesson

The team built the specification correctly—but the specification did not represent the real need. Verification passed; validation exposed the gap.

Mentor Insight

Verification cannot rescue a bad requirement by itself. A perfectly implemented wrong requirement is still wrong software. Validation is where engineers challenge whether their models correspond to reality.

Key Takeaway

Verification: implementation conforms to specification — “Are we building the product right?” Validation: the model/product corresponds to the real world and customer need — “Are we building the right product?” Reviews, walkthroughs, inspections, peer review, desk checking, and testing provide different forms of V&V evidence across the life cycle.

Think Like a Software Engineer

Every test case passes. Can validation still fail?

Yes or no? Decide whether passing tests proves that the requirements themselves represent what customers actually need.
