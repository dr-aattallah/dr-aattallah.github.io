CPCS 351 / Topic 05 / Use Case Guidelines
Clarity over completeness

One readable diagram beats one giant diagram.

Use case diagrams simplify communication only when scope, grouping, naming, and relationships remain understandable. Complex systems need several focused views.

Divide by subsystem or stakeholder goal. Separation of concerns is a modeling skill, not only a coding principle.

Diagram checklist

Keep the model focused

  • Give the system or subsystem boundary a meaningful name.
  • Show only actors and use cases relevant to the chosen scope.
  • Use several diagrams for closely related groups instead of one crowded diagram.
  • Avoid many single-use-case diagrams that hide the overall context.
  • Use actor generalization when it genuinely removes repeated associations.
  • Keep only use cases and their relationships inside the system boundary.
  • Do not add «include» or «extend» unless the dependency meaning is useful.
Inside or outside?

The boundary controls interpretation

Inside the boundary

Use cases—the externally visible services or goals supported by the subject.

Outside the boundary

Actors—people, organizations, devices, or other systems interacting with the subject.

Do not place inside: database tables, screens, implementation classes, hackers as internal components, technical layers, or step-by-step flow logic.
Worked interpretation

Hospital reception as a focused subsystem

The lecture’s hospital example is useful because it chooses one module within a larger hospital system. The receptionist’s goals remain readable: scheduling appointments, admitting patients, collecting information, allocating beds, receiving payments, and supporting insurance documentation.

Modeling workflow

Build from goals, then refine

1. Define scopeName the subject and decide what lies outside.
→
2. Identify actorsList external roles seeking or providing services.
→
3. Find goalsWrite complete, valuable verb–noun use cases.
→
4. Add relationshipsUse only relationships that improve meaning.
→
5. Review readabilitySplit the view if the story is no longer obvious.
Mentor insight

A diagram is a communication view, not the entire use case model. Detailed flows, alternatives, preconditions, and business rules normally belong in accompanying textual specifications.

Key takeaway

Define a meaningful boundary, keep actors outside and use cases inside, group related goals, and remove relationships that create visual noise rather than insight.
