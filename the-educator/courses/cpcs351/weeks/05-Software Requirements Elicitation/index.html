Topic 05 · Requirements Engineering

Discover what the system must deliver.

Requirements elicitation is the disciplined work of identifying the real capabilities, constraints, priorities, and quality expectations for a software system—before costly assumptions become code.

Start with the problem and the people. A feature list is useful only when it represents real stakeholder needs.

The planning phase

Three connected planning activities

The lecture places elicitation at the start of a planning sequence. The team collaborates with customers and users to identify business needs, derive use cases, prioritize requirements, and build an iterative development plan.

Core definition

A requirement states a capability or constraint

Lecture baseline: Requirements are capabilities that the system must deliver. They are documented in a requirements specification that can form part of the agreement between customer and developer.

Identify

Reveal problems, users, goals, and the current business situation.

Formulate

Turn discoveries into clear functional and non-functional requirements.

Check

Evaluate feasibility, correctness, consistency, and testability.

Learning outcomes

What you should be able to do

Justify requirement types

Distinguish functional from non-functional requirements and explain why each matters.

Apply elicitation methods

Use suitable information-collection and analysis methods for a medium-sized system.

Model user goals

Use UML use case notation and relationships to communicate high-level functional requirements.

Mentor insight

Elicitation is not simply asking, “What do you want?” Stakeholders often know their problems better than the software solution. The analyst must help transform experience and goals into testable requirements.

Key takeaway

The planning phase begins by discovering the right requirements, translating them into user-centered models, and prioritizing them for iterative delivery.
