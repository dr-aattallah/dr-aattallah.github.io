Reuse, Flexibility, Obsolescence, Portability & Testability

Design not only for today, but for reuse, future change, technology evolution, multiple platforms, and reliable testing.

14of 14
  • Increase reusability: generalize designs where possible, apply good cohesion/coupling/abstraction, provide hooks for extension, and simplify the design.
  • Reuse existing designs and code: benefit from prior investment in reusable components; design with reuse complements design for reusability.
  • Code cloning is not good reuse because every copied occurrence must be changed when defects are fixed or behavior changes.
  • Design for flexibility: anticipate future changes; reduce coupling, increase cohesion, create abstractions, avoid hard-coding, leave options open, avoid unnecessary restrictions on future maintainers, and use/make reusable code.
  • Anticipate obsolescence: plan for technology/environment change so software can continue to run or be changed easily.
  • Avoid early technology releases, environment-specific libraries, undocumented or little-used library features, and special software/hardware from vendors unlikely to provide long-term support.
  • Prefer standard languages and technologies supported by multiple vendors.
  • Design for portability: run on as many platforms as practical and avoid facilities specific to one environment, such as a library only available on Microsoft Windows.
  • Design for testability: make testing easy to automate; functionality should be drivable by external test programs without depending on a GUI.
  • The source suggests using a Java main() method in a class to exercise its other methods as a simple test-driving mechanism.
