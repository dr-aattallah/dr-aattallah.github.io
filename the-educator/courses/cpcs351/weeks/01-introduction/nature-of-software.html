Topic 01 · Section 1

The Nature of Software

Software is fundamentally different from physical engineering products. Understanding these differences helps explain why software needs its own engineering discipline.

Original Lecture Content

What makes software different?

01

Software is intangible

Software has no physical form. Unlike a bridge, machine, or building, you cannot directly see the full structure of a software system.

Original lecture point: this makes development effort hard to understand.
Modern Example

A mobile banking app may look simple on the screen, but behind it may be authentication services, payment systems, fraud detection, databases, APIs, logging, security controls, and cloud infrastructure. Most of that complexity is invisible to the user.

02

Software is easy to reproduce

Once software has been developed, creating another copy is inexpensive. The major cost is in designing and developing the original software.

Original lecture comparison: in many traditional engineering products, manufacturing is the costly stage.
Example

Developing the first version of an application can require months of work. Distributing an additional digital copy to another user may cost almost nothing compared with manufacturing another physical car, laptop, or machine.

03

The software industry is labor-intensive

Software development depends heavily on human analysis, design, communication, programming, testing, and decision-making.

Original lecture point: software development is hard to automate completely.
Updated Perspective

Modern tools and AI can automate parts of coding, testing, deployment, and documentation, but engineers still need to understand the problem, make architectural decisions, validate requirements, assess risks, and decide whether the generated solution is correct.

04

Untrained people can build software

It is possible to assemble software without following disciplined engineering practices.

Original lecture point: quality problems may be difficult to notice.
Example

A small web application may appear to work correctly during a demo, while still containing security weaknesses, poor error handling, duplicated logic, or architectural problems that only become visible after real users begin using it.

05

Software is easy to modify

Software can often be changed quickly because there is no need to rebuild a physical product.

Original lecture warning: people may make changes without fully understanding the software.
Realistic Scenario

A request such as “add one field to checkout” may affect validation, payment processing, database schemas, tax calculations, receipts, analytics, APIs, and mobile applications. A small visible change can have a large hidden impact.

06

Software does not “wear out” physically

Software does not deteriorate because physical components become worn. Instead, its design can deteriorate as changes accumulate.

Original lecture: deterioration can result from erroneous changes or changes that were not anticipated, making the software increasingly complex.
Analogy

Imagine repeatedly extending a house without updating its original architectural plan. The building may still stand, but every new change becomes harder and riskier. Software can experience the same kind of structural deterioration.

Concept Comparison

Physical products vs. software

Physical Engineering Product
Software
Manufacturing another unit has significant cost.
Reproducing another digital copy is inexpensive.
Structure can often be physically inspected.
Internal structure is largely intangible.
Physical components wear with use.
Software design deteriorates mainly through changes and increasing complexity.
Manufacturing may dominate production cost.
Most cost is concentrated in development and maintenance.
Key Takeaway

Software is easy to copy and modify, but difficult to visualize, estimate, and evolve safely. These characteristics are a major reason why disciplined software engineering processes are necessary.

Think Like a Software Engineer

“It is only a small change.” Is it really?

A customer asks you to add one new field to an online checkout page. Before changing the code, what other parts of the system would you investigate? Think about data storage, validation, APIs, payment processing, testing, analytics, and other dependent components.
