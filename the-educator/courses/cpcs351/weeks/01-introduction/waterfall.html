The Waterfall Process

The Waterfall Process organizes development into a sequence of major phases. Each phase produces work that becomes the basis for the next phase.

“Waterfall is easy to understand because the phases flow downward in a clear sequence.”
— Your Software Engineering Mentor

From the Original Lecture

The seven Waterfall phases

The original lecture presents the Waterfall Process in this order: System Engineering, Software Requirements Analysis, Software Design, Coding & Unit Testing, Integration & Integration Testing, Acceptance Testing, and Maintenance.

01
System Engineering
System context, scope, constraints, feasibility
02
Software Requirements Analysis
Software requirements and expected capabilities
03
Software Design
Architecture, models, interfaces, data design
04
Coding & Unit Testing
Implemented units with unit-level verification
05
Integration & Integration Testing
Combined components and verified interactions
06
Acceptance Testing
Evidence that the system satisfies acceptance expectations
07
Maintenance
Fixes, adaptations, enhancements, ongoing support

What Happens in Each Phase?

From problem understanding to long-term evolution

System Engineering

Understand the broader system, environment, major constraints, stakeholders, and boundaries before focusing only on software.

Requirements Analysis

Determine what the software must do, what constraints apply, and what capabilities the users and organization expect.

Software Design

Translate requirements into a technical solution structure: architecture, components, interfaces, data, and detailed design decisions.

Coding & Unit Testing

Implement the design in source code and verify individual units or components independently.

Integration & Integration Testing

Combine components and verify that interfaces, data exchanges, and interactions work correctly together.

Acceptance Testing

Evaluate whether the complete system satisfies the agreed requirements and acceptance expectations.

Maintenance

After deployment, correct defects, adapt to changing environments, and evolve the system as needs change.

Modern Example

University registration system

One system through the Waterfall sequence

How the phases might appear in practice

System Engineering Study the university ecosystem, SIS integration, identity systems, infrastructure, regulations, registration policies, and operational constraints.
Requirements Specify course search, registration, prerequisite checking, schedule conflict detection, seat capacity, security, and reporting requirements.
Design Define architecture, services, database schema, APIs, user flows, permissions, and integration interfaces.
Coding & Unit Testing Develop individual modules and verify registration rules, validation functions, service logic, and other units.
Integration Testing Verify that course data, prerequisites, student records, authentication, notifications, and other components work together.
Acceptance Testing Confirm with university stakeholders that the complete solution meets agreed expectations before release.
Maintenance Fix production defects, support policy changes, improve performance, and add future capabilities.

A Useful Perspective

Why Waterfall is easy to understand—and where it can be difficult

Why the model is useful

  • Clear phase boundaries
  • Easy to explain and visualize
  • Strong emphasis on documentation and deliverables
  • Useful when requirements are stable and changes are limited

Where problems may appear

  • Real requirements can change during development
  • Feedback may arrive late if working software appears late
  • Incorrect early assumptions can be expensive to fix later
  • Strictly sequential execution may be too rigid for uncertain projects
Mentor Insight

The lecture uses Waterfall to make the life-cycle phases concrete. Later methodologies may organize the same fundamental activities differently—iteratively, incrementally, or with more frequent feedback.

Key Takeaway

Waterfall presents a sequential view of development: System Engineering → Requirements → Design → Coding & Unit Testing → Integration & Integration Testing → Acceptance Testing → Maintenance.

Think Like a Software Engineer

A major requirement changes during coding. What happens?

Trace the impact backward and forward. Which earlier deliverables may need revision, and which later phases could be affected by the change?
