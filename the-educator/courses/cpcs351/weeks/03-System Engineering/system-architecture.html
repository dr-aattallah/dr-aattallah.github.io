System Architecture

Architecture turns one large system into a hierarchy of subsystems with clear responsibilities, controlled dependencies, and interfaces that allow separate teams to build parts that can still fit together.

“A good architecture does not merely divide the system. It divides it in a way that makes development, reuse, and integration easier.”

Visual Hook

The Responsibility Blueprint

System Architectural Design decomposes the complete system into a hierarchy of functionally cohesive, loosely coupled subsystems. Requirements are partitioned and assigned to those subsystems.

AIRPORT BAGGAGE HANDLING SYSTEM
↓

The architectural goal is not “more boxes.” Each subsystem should have a well-defined function, own a meaningful portion of the requirements, remain relatively independent, and still be easy to integrate.
Decomposition Guidelines

Six tests for a good subsystem boundary

1
Separate Team Development

The decomposition should allow separate engineering teams to develop the subsystems.

2
Support COTS Reuse

The structure should facilitate commercial off-the-shelf components when useful.

3
Partition Requirements

Subsystems should partition, or nearly partition, the system requirements.

4
Well-Defined Functionality

Each subsystem should have a clear and coherent purpose.

5
Relative Independence

Subsystems should minimize unnecessary dependencies on one another.

6
Easy Integration

The final pieces must be practical to connect and operate together.

Cohesion, Coupling & Reuse

Architecture should simplify the future

Poor Decomposition

Responsibilities are mixed, teams interfere with each other, requirements overlap heavily, and every change crosses many subsystem boundaries.

→

Better Decomposition

Mentor Insight

A subsystem boundary is an engineering decision. If the boundary does not reduce complexity, clarify ownership, support reuse, or simplify integration, it is probably the wrong boundary.

Key Takeaway

System Architectural Design decomposes the system into a hierarchy of functionally cohesive, loosely coupled subsystems. The decomposition should support separate teams, reuse of COTS parts, requirement partitioning, well-defined functionality, relative independence, and easy integration. System requirements are then assigned to the resulting subsystems.

Think Like a Software Engineer

Would you split a university system into “Database Subsystem,” “Screen Subsystem,” and “Business Logic Subsystem”—or by major university functions?

Which decomposition would better support separate teams, clear responsibilities, requirement ownership, reuse, and integration?
