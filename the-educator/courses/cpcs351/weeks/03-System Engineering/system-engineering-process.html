System Engineering Process

System Engineering organizes the journey from business need to an operational system. It works top-down, coordinates multiple disciplines, and reconnects independently developed subsystems through integration and testing.

“Start with the whole system, break it down carefully, let teams build the parts, then integrate everything back into one working system.”

Mental Model

Think in levels: System → Subsystems → Components

A formal system hierarchy becomes easier to understand when we use something familiar: a university smart campus.

UNIVERSITY SMART CAMPUS SYSTEM The whole university ecosystem
Academic · Finance · Transportation · Facilities Major subsystems
Registration · Attendance · Exams · Library · Bus Tracking Sub-subsystems / major functional parts
Student App · Database · Server · Network · Sensors · APIs Components and basic building blocks
Top-Down Thinking

Start with the complete mission, then divide the system into manageable parts.

Different Teams

Different subsystems may be developed by different engineering teams.

Integration Still Matters

Independent development is useful only if the pieces can later work together.

The same logic applies to ABHS: Airport System → ABHS → subsystem functions → hardware/software/human components.

1. System Requirements Definition

  • Identify business needs.
  • Define system requirements.
  • Conduct feasibility study.
  • Produce a project plan.

2. System Modeling & Design

  • Design system architecture.
  • Partition system requirements.
  • Allocate system requirements to subsystems.
  • Define subsystem functions.
  • Define subsystem interfaces and interaction behavior.

Hardware Development

  • Conduct subsystem architectural design.
  • Conduct subsystem component design.
  • Construct and evaluate functional prototypes.
  • Construct and test subsystems/components.

Software Development

  • Software requirements analysis.
  • Software design.
  • Implementation & unit testing.
  • Integration testing & acceptance testing.

Human Resource Development

  • Organize human resources.
  • Define job responsibilities, qualifications & skills.
  • Define operating procedures.
  • Recruit & train employees.

3. System Integration & Testing

  • Integrate subsystems.
  • Conduct system integration testing.
  • Conduct acceptance testing.
  • Conduct performance testing.

4. System Deployment

  • Install system in target environment.
  • Test system by users.

5. System Maintenance

  • Fix field-detected defects.
  • Perform system enhancements.

How to Read the Process

Three things happen at the same time

↓
Top-Down Decomposition

The system starts as one mission, then requirements and responsibilities are divided into smaller pieces.

↔
Multidisciplinary Interaction

Hardware, software, and human-resource teams communicate because subsystem decisions affect one another.

⇣
Bottom-Up Integration

After the parts are developed, they must be brought together and tested as one system.

Example · Airport Baggage Handling System

Watch ABHS move through the process

Define Move baggage correctly, support tracking, detect prohibited items, and serve required passenger volume.
Design Divide the system into terminals, conveyors, control software, scanners, tracks, and human roles.
Develop Hardware, software, and operating procedures are developed by specialized teams.
Integrate & Deploy Subsystems are connected, tested together, installed in the airport, and tested by users.
Maintain Field defects are corrected and the system is enhanced as airport needs evolve.

Mentor Insight

A system engineer does not simply manage boxes in a diagram. The real job is to make subsystem boundaries, responsibilities, interfaces, and integration decisions fit the system mission.

Key Takeaway

System Engineering moves from needs and requirements to architecture, parallel subsystem development, system integration and testing, deployment, and maintenance. Hardware, software, and human-resource development interact throughout the process.

Think Like a Software Engineer

If all three subsystem teams finish successfully, what can still cause the whole system to fail?

Think about incompatible interfaces, incorrect assumptions, missing responsibilities, integration problems, and target-environment constraints.
