# دليل تشغيل واستعادة نظام الحضور

## أهداف الخدمة

- فحص البوابة وSupabase كل 15 دقيقة.
- نسخة قاعدة بيانات يومية الساعة 01:15 بتوقيت الرياض.
- الاحتفاظ بنسخ GitHub Actions لمدة 30 يومًا.
- اختبار استعادة معزول مرة كل شهر وبعد أي مهاجرة كبيرة.
- هدف زمن الاستعادة (RTO): أربع ساعات.
- هدف نقطة الاستعادة (RPO): 24 ساعة كحد أقصى.

## تفعيل النسخ الاحتياطي

تحتاج إجراءات GitHub إلى السرّين التاليين:

1. `SUPABASE_DB_URL`: سلسلة اتصال قاعدة الإنتاج مع `sslmode=require`.
2. `RESTORE_TEST_DATABASE_URL`: قاعدة PostgreSQL معزولة للاختبار فقط، ولا يجوز أن تشير إلى الإنتاج.

تضاف الأسرار من إعدادات المستودع: **Settings → Secrets and variables → Actions**.
لا تُحفظ كلمات المرور أو سلاسل الاتصال في المستودع.

## اختبار الاستعادة الشهري

1. افتح إجراء **Attendance database backup**.
2. اختر **Run workflow** وفعّل `verify_restore`.
3. تحقق من نجاح `pg_restore` وفحص جدول `attendance_sessions`.
4. دوّن رابط التشغيل وتاريخه في سجل التشغيل.
5. لا تستخدم قاعدة الإنتاج هدفًا للاستعادة مطلقًا.

## التراجع عن مهاجرة

1. أوقف الكتابة من واجهات الحضور إذا كانت سلامة البيانات معرضة للخطر.
2. التقط نسخة فورية قبل أي تغيير إضافي.
3. استخدم مهاجرة تراجعية جديدة ومراجَعة؛ لا تحذف سجل المهاجرات ولا تعيد كتابة مهاجرة منشورة.
4. اختبر المهاجرة التراجعية على قاعدة الاستعادة.
5. طبّقها على الإنتاج ثم نفّذ فحوص لوحة التجربة وسلامة البيانات.

## الاستجابة لتنبيه

يفتح فحص المراقبة Issue بعنوان `[تشغيل] تعطل خدمة في نظام الحضور`.

1. افتح رابط تشغيل الإجراء داخل البلاغ وحدد نقطة الفشل.
2. افحص Supabase Status وGitHub Pages.
3. إذا كان العطل في الواجهة فقط، أعد آخر نشر ناجح.
4. إذا كان في قاعدة البيانات، أوقف العمليات المتأثرة وقيّم الحاجة للاستعادة.
5. بعد التعافي، تحقق من عدم وجود جلسات متعددة نشطة أو حضور مكرر أو سجلات يتيمة.
6. أغلق البلاغ بعد توثيق السبب ووقت التعافي والإجراء الوقائي.

## تصنيف الحوادث

- **حرج:** فقد بيانات، اختراق صلاحيات، أو عدم القدرة على تسجيل الحضور.
- **عالٍ:** فشل NFC أو الدخول لأكثر من شعبة.
- **متوسط:** تأخر الأعذار أو التقارير مع بقاء التسجيل متاحًا.
- **منخفض:** خلل عرض أو رسالة مساعدة غير صحيحة.
