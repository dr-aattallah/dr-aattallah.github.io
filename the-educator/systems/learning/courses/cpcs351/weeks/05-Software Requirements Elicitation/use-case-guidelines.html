Use-Case Diagram Guidelines

Good use-case diagrams communicate scope and goals; overloaded diagrams hide them.

6of 9 pages
Core lecture content Clarification & study aids
Learning focus

Justify functional and non-functional requirements and apply elicitation/analysis methods to produce software requirements.

Core lecture

What you need to understand

  • Avoid many use cases in one diagram, many one-use-case diagrams, excessive complexity, and unnecessary relationships.
  • Group closely related use cases and give each system/subsystem a meaningful name.
  • Use generalization when it truly simplifies repeated actor links.
  • Only use cases and their relationships belong inside the system boundary; actors remain outside.
Visual model

See the idea

Overloaded diagram
Focused subsystem diagram
Worked example

SAMS

Instead of one crowded diagram, separate Authentication, Program Management, User Management, and End-User Search into focused subsystem views.

Remember

A use-case diagram is a communication tool: show the minimum relationships needed to understand scope and goals.
