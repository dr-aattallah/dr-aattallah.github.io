Software Development Process & the Waterfall Example

Follow development from the initial system concept to an operational system—and connect every phase to the artifact or evidence it produces.

6of 8 lessons
From idea to operationWhat has to happen between “we need a system” and “the system is running in its target environment”?
Learning Focus

Explain how the development process transforms a concept into an operational system, correctly order the Waterfall phases, and identify representative deliverables/evidence produced along the way.

Development Process

What the Process Must Do

A software development process transforms the initial system concept into the operational system running in the target environment. It identifies business needs, conducts a feasibility study, formulates requirements/capabilities, and then designs, implements, tests and deploys the system.

CLO Coverage · Phase → Evidence

What Each Phase Produces

The lecture names the phases; the examples below make the phase outputs concrete. Exact document names vary by organization, but each phase should leave evidence that supports the next.

1 · System EngineeringSystem concept, business need, scope/context and feasibility evidence.
2 · Requirements AnalysisSoftware Requirements Specification (SRS) or equivalent agreed requirements.
3 · Software DesignArchitecture and detailed design models/specifications.
4 · Coding & Unit TestingSource code, executable units and unit-test results.
5 · Integration & TestingIntegrated build plus integration-test results and defect evidence.
6 · Acceptance TestingAcceptance results showing whether the delivered system satisfies agreed needs.
7 · MaintenanceChange requests, fixes, revised artifacts and updated releases.

How to Read It

Waterfall Is an Organization of Development Work

The model makes the progression visible: understand the system context and requirements before design; design before implementation; test units and integrations; validate through acceptance testing; then maintain the delivered system. Later topics can critique or compare lifecycle models, but here the priority is understanding the sequence and purpose of these phases.

Put the Phases Back in Order

Design, Acceptance Testing, Requirements Analysis, Coding & Unit Testing. Which comes first, and what evidence should flow forward?

Self-feedback: Requirements Analysis → Design → Coding & Unit Testing → Acceptance Testing. Requirements guide design; design guides implementation; implementation produces executable software; acceptance provides evidence against agreed needs.
