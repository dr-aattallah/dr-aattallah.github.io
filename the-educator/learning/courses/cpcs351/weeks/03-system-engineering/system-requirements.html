System Requirements

Before deciding which subsystem will do the work, engineers must establish what the complete system must achieve and the constraints under which it must operate.

3of 8 pages
Learning focus

Derive system requirements from goals and needs, distinguish capabilities from constraints, and explain why requirements precede allocation.

From problem to specification

Requirements do not begin with a solution

Business goals
→
Current situation
→
Stakeholder needs
→
Feasible selection
→
System requirements

Engineers first understand the organization and existing operation. Needs may exceed what budget, schedule, technology or regulation allows, so a feasible subset is selected and expressed as system-level requirements.

What requirements cover

More than functionality

Capabilities

Services and outcomes the complete system must provide.

Performance

Throughput, response time, capacity and other measurable targets.

Quality

Reliability, availability, safety, security and other quality expectations.

Interfaces

Required interactions with users, devices, organizations and external systems.

Constraints

Budget, schedule, standards, regulation, physical limits and mandated technology.

Information collection

How engineers learn about the system

The lecture emphasizes multiple complementary sources: presentations, observation and study of current operations, surveys, interviews, and literature/document review. No single technique guarantees a complete picture.

Worked example

ABHS: from vague need to testable requirement

Vague need: “Handle busy travel periods.” Better system requirement: “The baggage-handling system shall process the specified peak baggage volume while meeting the required routing accuracy and availability.” The exact measurable values belong in the real specification. Only afterward are those targets allocated to check-in, conveyors, scanners, software and staff.

Misconception: “A system requirement should already say which software module implements it.”

Not necessarily. System requirements describe the whole-system obligation. Allocation is the later design decision that assigns responsibility to subsystems.

Key takeaway

Define what the whole system must achieve before deciding where each responsibility belongs.
