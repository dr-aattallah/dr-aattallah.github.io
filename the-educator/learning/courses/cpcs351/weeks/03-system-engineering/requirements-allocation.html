Requirements Allocation

A system requirement becomes actionable only when responsibility for satisfying it is assigned to one or more subsystems.

5of 8 pages
Learning focus

Allocate whole-system requirements to subsystems while preserving coverage, traceability and shared performance constraints.

The allocation question

Who is responsible for satisfying this requirement?

Some requirements map cleanly to one subsystem. Others—especially performance, safety, reliability and end-to-end behavior—must be decomposed across several. Allocation connects the system specification to concrete engineering responsibility.

Allocation rules

What a good allocation preserves

Coverage

Every selected system requirement has an implementation responsibility.

Traceability

Engineers can trace from a system need to the subsystem obligations that satisfy it.

Feasibility

Allocated targets are realistic for the chosen technology and subsystem.

Consistency

Local targets combine to satisfy the original whole-system target.

Worked example · performance allocation

ABHS throughput

Suppose the complete system must support a defined peak baggage throughput. That one system-level target may become capacity requirements for check-in stations, conveyor segments and scanners; latency requirements for routing software; and staffing/procedure requirements for exception handling. Optimizing only one subsystem does not guarantee the end-to-end target.

Misconception: “Allocation means copying the same requirement into every subsystem specification.”

Allocation assigns or decomposes responsibility. Each subsystem receives the part it must satisfy, while traceability preserves the relationship to the original system requirement.

Key takeaway

Architecture says what the parts are. Allocation says what each part is accountable for.
