Topic 03 · Lesson 08

System Configuration Management

A system can contain individually correct components and still fail because the versions assembled together are incompatible.

8of 8 pages
Learning focus

Explain how configuration identification, change control, version coordination and baselines protect consistency across an evolving system.

The version problem

Correct parts can form the wrong system

Hardware, firmware, software, documents and operating procedures evolve at different speeds. Configuration management records what belongs together and controls changes so that a released system is a known, reproducible and compatible configuration.

Configuration identification

Identify the controlled components and their versions.

Change control

Evaluate, approve and coordinate changes instead of allowing uncontrolled local updates.

Baseline

A formally established, consistent configuration used as a reference for development, test or release.

Status / traceability

Know what changed, why, when, and which system configuration contains it.

Worked example

ABHS release

A routing-software update expects a new scanner protocol. Deploying it while some terminals still use older firmware can break baggage events even though both versions work correctly in their intended configurations. Configuration management prevents that accidental combination or explicitly verifies compatibility before release.

Misconception: “Configuration management is just Git for source code.”

Version control is one supporting mechanism. System configuration management is broader: it coordinates compatible versions of software, firmware, hardware, documents, procedures and other controlled system items.

Topic 03 · Key takeaways

Rebuild the system-engineering story

  1. System engineering optimizes the whole system across software, hardware, people, procedures and environment.
  2. System requirements define whole-system capabilities and constraints before subsystem responsibility is chosen.
  3. Architecture decomposes the system into coherent subsystems with explicit interfaces.
  4. Requirements allocation assigns whole-system obligations to accountable subsystems while preserving traceability.
  5. Different architectural diagrams answer different structural, interface and flow questions.
  6. Integration and system testing expose incompatibilities that isolated subsystem testing cannot.
  7. Deployment places the system in its real operational environment; maintenance changes an already interdependent system.
  8. Configuration management preserves a known compatible system as its parts evolve.
