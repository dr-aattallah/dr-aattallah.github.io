Topic 03 · Lesson 08

System Configuration Management

Configuration management keeps the evolving combination of hardware, software, procedures and other system components identifiable, controlled and mutually compatible.

8of 8 pages
Learning Focus

Explain why system configuration management is necessary, name its four functions, apply them to a multi-version system, and reconstruct the complete Topic 03 story.

Why configuration management is needed

A system changes in more than one place at a time

The lecture gives two key reasons. First, a system may have different versions and releases for different customers. Second, multiple engineering teams may update system configuration concurrently. Without coordination, individually valid components can form an incompatible system.

Configuration management is therefore performed during both the development phase and the maintenance phase.

Four official SCM functions

Identify → control → audit → report

1 · Configuration Identification

Identify configuration items, versions, relationships and approved baselines so the team knows exactly what constitutes a system release.

2 · Configuration Change Control

Evaluate, approve, coordinate and record proposed changes so one team does not silently break another subsystem or release.

3 · Configuration Auditing

Check that the actual system configuration matches the approved specification and that required changes were implemented correctly.

4 · Configuration Status Reporting

Report the current state of configuration items, versions, approved changes and baselines so stakeholders know what is deployed or under development.

Worked example

ABHS release compatibility

A new ABHS software version expects a new scanner protocol. Configuration identification tells us which software and firmware versions belong together. Change control prevents deploying the software before the scanner update is approved. Auditing checks that the installed airport configuration matches the approved release. Status reporting tells operations which terminals have migrated and which still run the previous baseline.

Topic 03 · rebuild the story

From system boundary to controlled evolution

1
Define the system.

Recognize interacting components, system hierarchy, environment and evolution.

2
Apply the system-engineering process.

Move top-down from goals and requirements to design, then bottom-up through integration, deployment and maintenance.

3
Define system requirements.

Use multiple information sources to identify capabilities, constraints, priorities and quality/performance/security needs.

4
Design the architecture.

Decompose the system into coherent, relatively independent and integrable subsystems.

5
Allocate requirements.

Refine whole-system obligations into measurable subsystem/component responsibilities while preserving traceability.

6
Visualize the architecture.

Choose block, UML component, SysML or data/material-flow views according to the engineering question.

7
Integrate and deploy.

Test interoperability, system requirements and real target-environment behavior.

8
Control evolution.

Use configuration management to keep versions and concurrent changes consistent.

Misconception: “Configuration management is just source-code version control.”

No. System configuration management covers the coordinated versions and changes of all relevant system components—including hardware, software and operational artifacts—not only code.

Key takeaway

System engineering begins with the whole-system mission and continues through requirements, architecture, allocation, multidisciplinary development, integration, deployment and controlled evolution.
