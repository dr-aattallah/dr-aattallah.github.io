Integration, Deployment, and Maintenance

Subsystems developed by different engineering teams must interoperate as one system, satisfy the system requirements, work in the target environment, and remain consistent as they evolve.

7of 8 pages
Learning Focus

Explain why subsystem development requires collaboration, distinguish integration testing from system and deployment testing, and identify cross-subsystem problems that appear late if interfaces were poorly coordinated.

Other system engineering activities

Development is distributed across engineering teams

The lecture emphasizes that different engineering teams develop different subsystems. These teams must collaborate to solve interdisciplinary problems because subsystem assumptions are connected through interfaces, shared constraints and the system mission.

Three stages

Integrate → verify in the environment → maintain

1 · System Integration & Testing

Combine subsystems and components, test interoperability, and verify that the complete system satisfies system requirements and constraints.

2 · System Deployment

Install the system in the target operational environment and test it there—not only in the development environment.

3 · Maintenance & Evolution

Coordinate later changes across interdependent hardware, software and human procedures while preserving system integrity.

Subsystems can each pass their local tests and still fail when connected. Integration testing therefore evaluates the relationships among parts, while system testing evaluates whether the complete integrated system satisfies the required behavior.

Worked example

ABHS airport upgrade

Suppose a new scanner is introduced. The scanner hardware may work perfectly, but deployment can still fail if its firmware uses a new protocol, the control software expects the old message format, conveyor timing changes, monitoring dashboards interpret alarms incorrectly, or staff procedures are outdated. System engineering treats the change as a coordinated system change—not as a device replacement.

Transfer example · Smart Hospital

Medication delivery robot release

Subsystem test: the robot navigates correctly and the scanner reads wristbands. Integration test: robot, scanner and medication-verification software exchange the right data. System test: the entire workflow satisfies patient-identification, delivery-time and safety requirements. Target-environment test: the system is exercised on real wards with elevators, Wi-Fi dead zones, clinical interruptions and actual nurse procedures.

Apply it · Which test level found the problem?

Scenario: Every subsystem passed locally, but when connected, the scanner sends patient IDs with leading zeros while the verification software removes them, causing false mismatches.

Reveal reasoning: This is an integration problem: each part may be locally correct, but their interface semantics are incompatible.

Misconception: “If every subsystem passes its own tests, the system is ready.”

No. Local correctness does not prove interoperability or whole-system compliance. The assembled system must be integrated, tested against system requirements and constraints, then tested in its target environment.

Key takeaway

Integration proves that the parts can work together; system testing proves the whole meets its obligations; deployment proves it can work in the real environment; maintenance keeps that whole consistent as it changes.
