System Engineering Process

The process moves from whole-system needs to subsystem development and then back to an integrated, deployed and maintained whole.

2of 8 pages
Core Lecture Content Added Study Material
Learning Focus

Order the major system-engineering activities, explain the top-down and bottom-up movements, and show where hardware, software and human-resource development interact.

Process logic

Top down to define; bottom up to integrate

System engineering follows a top-down divide-and-conquer approach during definition and design: begin with the system mission, derive requirements, model the system, decompose it and allocate responsibilities. After the subsystems are developed, the direction reverses: engineers integrate and test the parts until the complete system is ready for deployment.

Interdisciplinary development

Subsystem work happens in parallel—but not independently

Hardware development

Devices, sensors, conveyors, processors, tracks and other physical components are engineered to satisfy allocated requirements and interfaces.

Software development

Control, data processing, interfaces, monitoring and other software capabilities are developed under the same system constraints.

Human-resource development

Roles, staffing, training, procedures and operational responsibilities are developed because people are part of the system.

These teams must collaborate on interdisciplinary problems. A hardware change can alter software timing; a software interface can alter operator procedure; a staffing assumption can affect throughput.

Stage by stage

What each phase contributes

1 · System Requirements Definition

Understand business goals and the current situation, derive needs, select the feasible subset, and express required system capabilities and constraints.

2 · System Modeling & Design

Decompose the system, choose subsystem boundaries, define interfaces, visualize the architecture and allocate requirements.

3 · Subsystem Development

Different engineering teams develop hardware, software and human/operational subsystems under agreed requirements.

4 · System Integration & Testing

Assemble subsystems, check interoperability and verify that the complete system satisfies system requirements and constraints.

5 · Deployment

Install the integrated system in the target environment and test it under real operational conditions.

6 · Maintenance

Manage changes and evolution while keeping the full system configuration consistent.

Worked example

Trace one ABHS need through the process

Need: move checked baggage to the correct destination reliably and on time. Requirements: define transport, throughput, locating and security obligations. Design: choose check-in, conveyor, scanner, control-software and human subsystems. Allocation: assign detailed responsibilities and quantitative targets. Development: teams build their parts. Integration: test baggage end-to-end. Deployment: install in the airport. Maintenance: coordinate later hardware, software and procedural changes.

Transfer example · Smart Hospital

The same process in a different domain

Goal: reduce medication-delivery delays. Need: deliver the correct dose to the correct patient reliably. Requirements: patient identification, dose verification, delivery time, availability and safety constraints. Design: pharmacy software, dispensing hardware, delivery robots, nurse workflow and interfaces. Development: each discipline builds its subsystem. Integration: verify robot, scanner, software and workflow interoperability. Deployment: validate the system on real wards. Maintenance: coordinate software, robot firmware and clinical-procedure changes.

Apply it · Where does this problem belong?

Scenario: The robot navigation subsystem works, the medication-order software works, but the hospital cannot release the system because nurses have not been trained on the emergency-stop procedure.

Reveal reasoning: This is not a software-only defect. Human-resource development is part of the system-engineering process; the system is not deployable until the human subsystem is ready.

Misconception: “Once requirements are written, each discipline can work independently until integration.”

No. The lecture explicitly emphasizes interaction among development activities. Interfaces, shared constraints and interdisciplinary issues require continuous coordination.

Key takeaway

System engineering decomposes the whole into developable parts, coordinates parallel engineering, then integrates the parts back into a tested whole.
