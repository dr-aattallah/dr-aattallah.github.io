Where OIM Fits in the Methodology

OIM is not an isolated UML exercise. It sits between understanding a use case and assigning software responsibilities.

Inputs → OIM → downstream design

Expanded use cases
Domain model
→
Behavior modeling & responsibility assignment
→
Design class diagram

During an iteration, expanded use cases tell us what behavior must occur; the domain model tells us which concepts exist. OIM explores how collaborating objects can realize that behavior. Its result contributes to behavior models and later design-class responsibilities.

Analysis question vs design question

Requirements / analysis

What does the actor need the system to accomplish?

Object interaction

Which objects collaborate, in what order, to produce that result?

Why this matters

Jumping directly from a use case to code hides responsibility decisions. OIM makes those decisions inspectable before implementation.
