From Sequence Diagram to Implementation

A sequence diagram is not decoration. Its messages, guards, loops, object creation, and state changes become concrete responsibilities and code.

Core visual · Library Checkout

Read the interaction first, then read the code

The diagram below reconstructs the lecture’s Checkout interaction in a clean study format. Follow it top-to-bottom. Each message is numbered so you can map it directly to the Java implementation that follows.

Translation rules

What each UML construct becomes in code

➡️Message → method call

getDocument(cn) becomes a method responsibility on DBMgr.

🔁loop → iteration

loop [for each cn] becomes a Java for loop over cnList.

🛡️guard → condition

[u != null] and [a] become if conditions.

✨create → constructor

«create» Loan(u,d) becomes new Loan(u,d).

🔄state change → object behavior

setAvailable(false) updates the Document state through its own method.

💾persistence message → repository call

saveLoan(l) and saveDocument(d) become DB/repository responsibilities.

Implementation

One possible Java realization

CheckoutGUI / controller responsibility

public class CheckoutGUI {
    private final DBMgr dbm = new DBMgr();

    public String process(String uid, String[] cnList) {
        User u = dbm.getUser(uid);          // 2
        if (u == null) return "Unknown user";

        for (String cn : cnList) {          // loop
            Document d = dbm.getDocument(cn); // 4

            if (d != null && d.isAvailable()) { // 5 + guard
                Loan l = new Loan(u, d);       // 6
                dbm.saveLoan(l);               // 7

                d.setAvailable(false);          // 8
                dbm.saveDocument(d);            // 9
            }
        }
        return "Checkout completed";          // 10
    }
}

Important: the exact Java architecture can vary. The sequence diagram does not prescribe every implementation detail. What it does reveal strongly is who receives each message and therefore who owns each responsibility.

Exam lens

When asked to move from a sequence diagram toward implementation, do not copy arrows mechanically. Ask: Who receives the message? What responsibility does that imply? Is it a call, loop, guard, creation, state change, or persistence action?
