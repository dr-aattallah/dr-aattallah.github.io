  5. Draw participants and messages in causal order.

  7. Explain two receiver responsibilities implied by messages.

Reveal suggested solution

Possible participant chain

Student→RegistrationUI→RegistrationController→Student record/Section→Enrollment→RegistrationUI

Possible normal interaction

  1. Student submits the requested section to RegistrationUI.
  2. UI delegates register(studentId, sectionId) to RegistrationController.
  3. Controller retrieves the Student and Section.
  4. Controller asks whether prerequisites are satisfied.
  5. Controller checks section capacity.
  6. Controller checks timetable conflicts.
  7. If all conditions hold, Controller creates Enrollment(student, section).
  8. The enrollment is saved and a success result returns to the UI.
Typical guards: [prerequisites satisfied][capacity available][no timetable conflict]

Responsibilities exposed by messages: the controller coordinates the use case; Student/Section answer domain questions; the Enrollment object represents the successful registration relationship. Other sound designs are possible if responsibilities remain coherent.
