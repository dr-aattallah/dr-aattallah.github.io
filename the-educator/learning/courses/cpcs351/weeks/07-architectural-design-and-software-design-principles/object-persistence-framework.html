Persistence, Client–Server & Other Styles

Some architectures isolate persistence technology; others organize service relationships across networked components.

Object-Persistence Framework

Hide storage technology behind a stable manager

🧠
Business Objects A · B · C

Use the object-oriented implementation language and should not depend directly on DB-specific details.

🛡️
DB Manager

This is a concrete architecture example of information hiding: business behavior is protected from database-specific implementation details.

Other mappings in the source

Know what is taught — and at what depth

🌐 Peer-to-Peer

The supplied lecture maps distributed, decentralized systems to Peer-to-Peer architecture, but does not provide the same detailed architectural diagram used for Client-Server.

🧠 Blackboard

The source maps heuristic problem-solving systems to Blackboard architecture, again without equivalent detailed development in the supplied slides.

Concept connection

What principle appears repeatedly?

✕ Direct dependency everywhere

Business components know DB details; clients know server internals; changes spread widely.

→

✓ Stable interfaces

Managers, servers and ports expose what other components need while hiding implementation decisions.

Remember

Persistence framework hides storage. Client-server organizes service requests. P2P and Blackboard are source mappings you should recognize without inventing extra lecture detail.
