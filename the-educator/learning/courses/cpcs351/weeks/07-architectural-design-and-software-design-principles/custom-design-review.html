Custom Architecture, Interfaces & Review

When no existing style is enough, design deliberately, specify boundaries, and review the result.

11of 14
Learning focus

Cover custom design, subsystem functions/interfaces/interactions, review, package views, architectural guidelines, and agile guidance.

  • Not all projects can reuse an existing architectural style; custom architectural design may be required.
  • Design patterns are useful building blocks for custom architectural design.
  • Allocate requirements and architectural objectives to subsystems and components.
  • Specify the functionality of each subsystem and component.
  • Specify subsystem and component interfaces.
  • Specify interaction behavior among subsystems and components.
  • Review to ensure requirements and architectural design objectives are satisfied.
  • Review to ensure software design principles are satisfied.
  • Review against security requirements, constraints, and secure-software design principles.
  • The N-tier package-diagram example contains GUI, network, business, and database packages, «import» dependencies, and public/private package elements such as Main, MainFrame, Checkout Dialog, Return Dialog, Checkout Controller, Return Controller, Loan, Document, Patron, and Database Manager.
  • Guidelines: adapt an architectural style when possible, apply software design principles, apply design patterns, check against objectives/principles, and iterate if needed.
  • Agile principles: value working software over comprehensive documentation and use the 20/80 idea — good enough can be enough.
