Use-Case Foundations

A use-case model asks a disciplined question: which external role wants what useful result from the system?

4of 9 pages
Core lecture content Clarification & study aids
Learning focus

Read and construct UML use-case diagrams using actors, use cases, system boundaries and relationships, and use them to express high-level functional requirements.

Core lecture

What a use-case model actually captures

  • A use-case diagram graphically depicts a useful subset of the larger use-case model so stakeholders can communicate about scope and behavior.
  • A use-case model describes user goals, interactions with the system, and the behavior the system must provide to satisfy those goals.
  • The most important model elements are actors, use cases, the subject/system boundary, and relationships.
  • Use cases are useful before a project for business understanding, during requirements elicitation for capturing expected behavior, during analysis/design for identifying candidate classes, and during testing for identifying test scenarios.

Notation reference

Use-case diagram elements and symbols

ElementTypical notationMeaningHow to use it correctly
Actor👤An external role played by a person, organization, device, or another system.Name the role, not a specific person. Keep actors outside the subject boundary.
Use CasePlace OrderA complete unit of useful behavior that produces a result of value for an actor.Use a clear verb–object goal name such as Withdraw Cash or Schedule Appointment.
Subject / System BoundarySystemThe system, subsystem, service, or component whose behavior is being modeled.Place applicable use cases inside; place actors outside; give the boundary a meaningful name.
Association━━━━Shows that an actor and a use case communicate or participate with one another.Use a solid line. Do not use it merely for decoration or to connect two use cases of the same subject.
«include»- - - -▷
«include»		Required reused behavior inserted into the base use case.Arrow points from the including/base use case to the included use case. Think must reuse.
«extend»- - - -▷
«extend»		Optional or conditional behavior added to a base use case that is already meaningful by itself.Arrow points from the extending use case to the base use case. Think may add.
Generalization──▷Specialization/inheritance among actors or among use cases.The hollow triangle points toward the more general parent. Use it when specialization genuinely simplifies repeated structure.
Extension PointRegistration
extension points		A named location in a base use case where extending behavior can be inserted.Relevant mainly when the precise location/condition of an «extend» relationship matters.
