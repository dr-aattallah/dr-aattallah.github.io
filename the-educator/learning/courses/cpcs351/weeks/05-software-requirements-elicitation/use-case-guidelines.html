Use-Case Diagram Guidelines

A good use-case diagram is a communication view, not a database of every possible relationship.

6of 9 pages
Core lecture content Clarification & study aids
Learning focus

Design focused use-case diagrams that communicate scope and goals while avoiding unnecessary complexity.

Official lecture guidelines

Clarity beats completeness on one canvas

⚠️ Avoid

  • Too many use cases in one diagram.
  • Many separate diagrams containing only one use case each.
  • Overly complex diagrams with crossing links.
  • Unnecessary «include» or «extend» relationships.
  • Actors, databases, internal objects or implementation elements placed inside the subject boundary.

🎯 Prefer

  • Several diagrams for coherent groups of closely related use cases.
  • Only actors and use cases relevant to the current view.
  • Meaningful system/subsystem names.
  • Generalization when it genuinely reduces repeated actor links.
  • Only use cases and their relationships inside the system boundary.
Official lecture example · SAMS

Decompose one overloaded diagram into focused subsystem views

The lecture contrasts an “Overly Complex!” SAMS diagram with smaller views. A clean decomposition might look like this:

🔐 Authentication

Start Up, Shutdown, Log In, Log Out.

📚 Program Management

Add Program, Delete Program, Edit Program.

👥 User Management

Create User, Delete User, Update User.

🔎 End-User Services

Search Programs, Display Program Detail, Apply Online.

This applies two general software-engineering principles explicitly named in the lecture: separation of concerns and divide and conquer.

Boundary rule

What belongs inside and outside?

Inside the boundary

Use cases and relationships among use cases that are applicable to the named system/subsystem.

Outside the boundary

Human actors, external systems/services, devices or other external roles that interact with the subject.

Actor–use case link

Always an association relationship in the lecture’s diagramming guidance.

Meaningful subsystem name

The name can later help suggest a package or module boundary in analysis/design.

Complexity trap

Do not add «extend» everywhere

The lecture shows a SAMS Program Management view made unnecessarily complex by adding multiple «extend» relationships to Login. If login is simply a precondition or common authentication concern, drawing many optional-extension arrows can obscure the real user goals. Use relationships only when their UML semantics add useful information.

External examples: compare your diagrams with the focused system examples at uml-diagrams.org — Use Case Diagram Examples. Look particularly at ATM, POS, e-Library, Online Shopping and Hospital Reception.
Memory hook

One diagram = one useful conversation. If the reader cannot immediately see the subject, actors and main goals, the view is probably too crowded.

Quick quality check

Before you submit a use-case diagram

Ask: Is the system boundary named? Are actors outside? Are use cases goal-oriented? Are only relevant elements shown? Does every «include»/«extend»/generalization have a defensible meaning? Could the diagram be split into a clearer subsystem view?
