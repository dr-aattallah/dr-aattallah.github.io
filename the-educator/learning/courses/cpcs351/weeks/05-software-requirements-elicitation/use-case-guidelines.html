Designing Clear Use-Case Diagrams

A good diagram is a communication view, not a warehouse for every actor and relationship.

7of 9 pages
Learning focus

Design focused use-case diagrams that communicate scope and goals without unnecessary complexity.

Official guidelines

Clarity beats completeness on one canvas

⚠️ Avoid

  • Too many use cases in one diagram.
  • Many one-use-case diagrams.
  • Crossing links and unnecessary relationships.
  • Actors, databases or implementation objects inside the boundary.

🎯 Prefer

  • Coherent groups of closely related use cases.
  • Only actors and goals relevant to the current view.
  • Meaningful system/subsystem names.
  • Generalization only when it reduces repetition.
Official SAMS lesson

Decompose one overloaded diagram into focused views

🔐 Authentication

Start Up, Shutdown, Log In, Log Out.

📚 Program Management

Add, Delete, Edit Program.

👥 User Management

Create, Delete, Update User.

🔎 End-User Services

Search, Display Detail, Apply Online.

This applies two lecture principles: separation of concerns and divide and conquer.

Boundary rule

Inside = system behavior; outside = external roles

Inside

Use cases and their relationships.

Outside

Human actors, devices and external systems/services.

Actor link

Actor–use case links are associations.

Subsystem name

A meaningful name can later suggest a package/module boundary.

Submission check

Is the boundary named? Are actors outside? Are goals clear? Are only relevant elements shown? Does every «include», «extend» or generalization have a defensible meaning?
