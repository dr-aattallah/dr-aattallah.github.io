Verification vs. Validation

Separate conformance to specification from correspondence to real customer needs.

3of 9 pages
HookA system can perfectly implement the wrong requirement. Is that success?

This is why software quality asks two different questions: conformance and real-world fitness.

Learning Focus

Distinguish verification from validation and identify which question each technique answers.

Verification — “Are we building the product right?”

Verification checks whether an implementation conforms to its specification. A lower-level abstraction implements a higher-level abstraction. For example, design verification checks whether software design satisfies the requirements specification.

Validation — “Are we building the right product?”

Validation checks correspondence between a model/product and the real world or real customer need. The lecture describes it as a process that seeks to refute a model. Functional testing is given as a validation technique.

Use the Abstraction Ladder

Customer Need
→
Requirements
→
Design
→
Code
→
Running System

Verification asks whether each lower-level representation correctly implements the higher-level one. Validation asks whether our representations and final system correspond to what is actually needed.

Common Misconception

“Verification is developer testing and validation is customer testing.” The lecture’s distinction is conceptual: conformance to specification versus correspondence to real needs.

Diagnose the Failure

A hospital system exactly implements “send reminders 24 hours before the visit,” but users actually need 48 hours because of transport constraints. Verification or validation problem?

Self-Feedback: The implementation may verify correctly against the written requirement, yet the requirement fails validation against the real-world need.
