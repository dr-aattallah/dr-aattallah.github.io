Behavior Modeling

Two complementary views of dynamic software: state modeling explains how one object reacts over its lifetime; activity modeling explains how work flows across actions, decisions, parallel paths, objects, and responsibilities.

Learning focus

Select and construct the right UML behavioral model from requirements, then connect behavioral discoveries back to software design.

Mental model first

Three questions, three UML views

Sequence

Conversation: Who sends what message to whom, and in what order?

State

Lifetime: What condition is one object in, and what event changes it?

Activity

Workflow: What work happens next, under what condition, in parallel, and by whom?

Logical learning path

From reactive object to system workflow

Requirements→Events & States→State Machine→Actions & Decisions→Concurrency→Swimlanes→Design

This sequence prevents a common mistake: drawing notation before deciding what behavioral question the model must answer.

Core lecture

Why combine these ideas?

  • Object State Modeling (OSM) addresses event-driven, state-dependent reactions to external stimuli.
  • Activity Modeling addresses transformational behavior: sequencing, branching, information/object flow, concurrency, synchronization, and workflow across subsystems.
  • They share behavioral concepts such as transitions and guards, but their modeling focus is different.
  • Together with sequence diagrams, they form a practical toolkit for describing dynamic system behavior.
Remember

Do not ask “Which UML diagram do I like?” Ask “What behavior am I trying to explain?”

Quick challenge

Which model?

A library book can be Available, Reserved, or Borrowed. An online order moves through payment, stock allocation, packing, and shipping. Which view fits each?

Reveal answer

Book: state machine—the same object changes condition over time. Order processing: activity diagram—the focus is workflow across actions and responsibilities.
