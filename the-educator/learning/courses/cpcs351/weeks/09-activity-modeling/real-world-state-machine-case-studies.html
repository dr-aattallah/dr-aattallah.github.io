Real-World State Machine Case Studies

Trace one object's lifecycle through states, events, guarded transitions, and outcomes using HungerStation and Snapchat.

14of 14 pages
Learning objectives

Identify the modeled object; distinguish a state from an event or action; interpret initial/final pseudostates, transition triggers, guards, entry/do/exit behaviors, and alternative terminal outcomes; relate state machines to sequence diagrams.

Start with the right question

What changes over the lifetime of one object?

A UML state machine diagram describes the states of one modeled object and the events that cause transitions between them. Unlike a sequence diagram, it does not primarily describe message exchange among several objects.

Reading notation: A filled black circle is the initial pseudostate; a bullseye is a final state. A rounded rectangle is a state. A labeled arrow represents a transition, commonly written event [guard] / effect. entry /, do /, and exit / denote state behaviors. Colors and annotations are visual aids, not formal UML semantics.
Case Study 01 · HungerStation

Order Lifecycle — From Draft to Completion

Modeled object: Order. Ahmed chooses two burgers, confirms delivery details, pays online or chooses cash on delivery, and waits for the restaurant and courier to fulfill the order. The same Order object changes state as events occur.

1. Order initiationDraft → Validating. Items, address and totals are checked.
2. Payment and acceptanceOnline approval or cash-on-delivery leads to Placed; the restaurant may accept or reject.
3. FulfillmentPreparing → Ready → Picked Up → In Transit → Delivered → Completed.
Open full-size diagram ↗Save PNG

Read the diagram in five steps

  1. Initial state: createOrder() starts the order in Draft.
  2. Guarded transitions: a valid order follows either [onlinePayment] or [cashOnDelivery].
  3. Alternative outcomes: payment failure permits retry or cancellation; the restaurant may reject the order.
  4. State behaviors: entry / notifyCustomer() runs on entering a state; do / prepareFood() represents activity associated with preparation.
  5. Termination: Completed, Rejected, and Cancelled lead to the final state.

Case Study 02 · Snapchat

SnapDelivery Lifecycle — From Created to Viewed or Expired

Modeled object: SnapDelivery, not the shared Snap. Sara sends a Snap to Ahmed. The system records this recipient's authorization, transmission, delivery, viewing and expiration independently from any other recipient.

1. Validate recipientCreated → Validating Recipient, then proceed or block according to privacy permissions.
2. Transmit and deliverSending → Sent → Delivered, with retry and pending alternatives.
3. Open and expireDelivered → Opening → Viewed → Expired, subject to availability and access checks.
Open full-size diagram ↗Save PNG

Read the diagram in five steps

  1. Object selection: one SnapDelivery record represents delivery to Ahmed, not the entire Snap.
  2. Guards: validation allows sending only when recipient permissions are satisfied.
  3. Retry loop: Send Failed → Sending models another transmission attempt.
  4. Distinct states: Sent, Delivered, and Viewed have different meanings.
  5. Terminal outcomes: the modeled delivery can become Expired, Blocked, or Cancelled.

Exam takeaway

Choose one object → identify meaningful states → identify events → add guarded transitions → model state behaviors → verify reachable outcomes. Do not confuse an event such as paymentApproved() with a state such as Placed.
