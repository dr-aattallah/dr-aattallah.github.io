Prototyping Model

A prototype is built early to learn what users actually need before committing to the complete solution.

5of 11 pages
Core lecture content Clarification & study aids
Learning focus

Explain how prototyping reduces requirements uncertainty, distinguish throwaway from evolutionary prototyping, and recognize why a prototype is primarily a learning instrument.

Core lecture · Visual anchor

Prototype to learn before you commit

When requirements are uncertain, the team does not pretend that everything is already known. It builds something visible and testable, lets users react to it, and uses that feedback to improve understanding.

?
Known Requirements

Start with what is currently understood—not with the assumption that the specification is complete.

⚡
Quick Prototype

Build a fast model of the uncertain or high-value parts of the experience.

LEARNThe prototype exists to reduce uncertainty.
👁
User Evaluation

Let real users interact, react, misunderstand, succeed and fail.

↺
Feedback

Capture missing needs, wrong assumptions, usability problems and new priorities.

✓
Refine Understanding

Update the requirements and decide whether another learning cycle is needed.

Memory hook: See → React → Learn → Refine. The value of prototyping is not the speed of drawing screens; it is the speed of discovering what the team misunderstood.
Two prototype paths

What happens after the learning?

Throwaway / Rapid Prototype

Build quickly to explore requirements, usability or feasibility. After the learning is captured, discard the prototype and engineer the real solution properly.

Learn → Discard
Evolutionary Prototype

Start with a working version and deliberately improve its structure and capabilities until it becomes part of the production system.

Learn → Grow
Three hooks to remember

Why prototyping works—and where teams go wrong

💡
Strength · Early Learning

Missing, misunderstood and unusable requirements surface before expensive downstream implementation.

↔
Mechanism · Feedback

The model gives users something concrete to react to instead of asking them to imagine an abstract specification.

⚠
Caution · Looks Real ≠ Ready

A convincing interface can still hide weak architecture, poor security, shortcuts and missing production-quality engineering.

Worked example

Clinic appointment interface

A clickable prototype reveals that users need family-member booking, clearer slot filters, and a simpler cancellation path before backend implementation begins. The prototype succeeds even if none of its code is reused—because it prevented the team from implementing the wrong workflow.

Remember

Prototype to learn. A prototype may look complete long before the engineering behind it is production-ready.

Added clarification

Connect it to engineering practice

Decision cue

Use prototyping when the biggest risk is not knowing what users really need, especially for novel workflows, interfaces or unclear requirements.

Exam lens

Be able to explain the feedback loop, distinguish throwaway and evolutionary prototyping, and explain why a prototype should not automatically be treated as production software.
