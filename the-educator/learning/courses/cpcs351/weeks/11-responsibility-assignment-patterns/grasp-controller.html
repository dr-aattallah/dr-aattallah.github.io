GRASP & the Controller Pattern

Protect the user interface from business responsibilities by introducing the first object beyond the UI that handles a system operation.

3of 8 pages

GRASP

GRASP patterns are general responsibility-assignment patterns: general because they apply to almost every software system, and responsibility-assignment because they address a central object-oriented design problem.

The chapter lists Controller, Expert, Creator, Low Coupling, High Cohesion, Polymorphism, Pure Fabrication, Indirection, and Do Not Talk to Strangers. It emphasizes Controller, Expert, and Creator as broadly applicable.

The checkout design problem

In the initial Checkout sequence, the GUI directly retrieves Documents, tests availability, creates Loans, saves business objects and updates availability. This creates tight coupling between presentation and business objects and gives the GUI too many responsibilities.

The better solution reduces coupling, removes irrelevant presentation responsibilities, supports separation of concerns/high cohesion, and introduces another object to handle actor requests.

Controller rule

Assign the responsibility for handling an actor request to a controller.

Actor requests should be handled in the business-object layer. The controller can delegate to or collaborate with business objects.

A use case controller can be assigned one-to-one with a use case: Checkout → CheckoutController; Login → LoginController. It maintains use-case state and can identify out-of-sequence system events.

Added example — Course Registration

Bad: RegistrationPage directly checks prerequisites, seat availability and creates Enrollment. Better: RegistrationPage sends register(studentId, sectionId) to RegistrationController, which coordinates domain objects.
