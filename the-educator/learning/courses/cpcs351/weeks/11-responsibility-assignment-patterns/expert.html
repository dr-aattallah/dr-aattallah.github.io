The Expert Pattern

Assign a responsibility to the object that already has the information required to fulfill it.

5of 8 pages

Information Expert rule

Start by clearly stating the responsibility.

Then assign it to the information expert — the class/object that has the information, typically an attribute, needed to fulfill that responsibility.

The chapter describes Expert as a basic guiding principle of OO design and notes that it is frequently applied while constructing object-interaction/sequence diagrams.

Checkout: ask who knows

Instead of asking DBMgr to decide whether a document is available, ask the Document, because Document has the availability information. In the improved sequence, the controller retrieves the domain objects, Document answers isAvailable() and updates its own availability, while the controller uses the parameters it has to create the Loan.

Reset Password example

The exercise initially assigns getQuest() and checkAns() to DBMgr. The chapter identifies this as wrong because DBMgr does not have the attributes needed to fulfill those requests. The improved design retrieves the User; User supplies its authentication question and checks the answer because User owns that information.

Benefits

  • Low coupling.
  • High cohesion.
  • Easier to comprehend and change.
  • Tends to produce “stupid objects” — infrastructure objects do not absorb domain intelligence that belongs elsewhere.

Added examples

Order.total() belongs with Order if it knows its line items. Section.hasSeat() belongs with Section if it stores capacity/enrollment. Account.canWithdraw(amount) belongs with Account if it knows the balance and withdrawal rules.
