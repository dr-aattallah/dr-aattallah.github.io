Finish by recognizing the design problem first, then selecting the responsibility-assignment rule.

Quick check

1. The UI receives checkout() and performs all business work. What is the first improvement?
Introduce a Controller to receive the actor/system request and coordinate domain objects.
2. Who should answer isAvailable() for a Document?
The information Expert: Document, if it owns the availability information.
3. Who should create a Chapter?
Book is a strong Creator because Chapter is part of/contained by Book.
4. What signals a bloated controller?
Too many unrelated requests, doing business work instead of delegating, and storing excessive domain information.
5. What is Singleton trying to control?
Construction/access so a class has a controlled number of instances — in the chapter's main case, one globally accessible instance.
6. Why is DBMgr not automatically the Expert?
Accessing stored data is not the same as owning the domain information/responsibility. Assign behavior to the domain object that has the relevant information.

One-minute map

Actor request → Controller. Knowledge → Expert. Creation → Creator. One controlled instance → Singleton.

Use Low Coupling and High Cohesion as quality tests for the assignments you make.

Exam-style challenge

For an online order, decide who receives placeOrder(), who computes the order total, and who creates an OrderLine. Do not answer from class names alone: justify each assignment using Controller, Expert, or Creator.

Design habit

State the responsibility explicitly before assigning it. That single habit prevents many procedural designs disguised as object-oriented code.
