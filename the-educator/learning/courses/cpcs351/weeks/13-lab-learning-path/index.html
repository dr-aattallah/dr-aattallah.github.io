Lab Learning Path

The lab is the applied spine of CPCS 351. It moves students from understanding a software problem to producing, checking and defending engineering artifacts. The original twelve lab files are preserved as the evidence base; this page reorganizes their skills and activities around the current The Educator topic sequence rather than treating the lab as a disconnected resource.

Purpose

What the lab is for

The original labs repeatedly require students to use UML/CASE tools, interpret software narratives, produce analysis and design models, apply design decisions, and connect selected exercises to the course project. The practical goal is therefore broader than drawing diagrams: students learn to convert software-engineering knowledge into defensible artifacts.

Learning outcomes

What students should be able to do

  • Use UML/CASE tools to create relevant analysis and design models.
  • Select and justify an appropriate software-development process for a scenario.
  • Define a problem, scope, stakeholders and domain before committing to a solution.
  • Write and distinguish functional and non-functional requirements.
  • Derive actors, use cases and system boundaries from requirements and narratives.
  • Construct domain/class diagrams with associations, multiplicities, generalization and whole–part relationships.
  • Model behavior using sequence, activity and state-machine diagrams.
  • Apply responsibility-assignment and design patterns such as Controller, Information Expert, Creator and Singleton where appropriate.
  • Reason about architectural organization using package/layered, client–server, N-tier, pipe-and-filter and MVC examples from the lab material.
  • Apply decomposition, modularity, reuse, information hiding and prototyping concepts to improve design quality.
Lab-by-lab map

The twelve source labs

LAB 01

Introduction to UML

Modeling foundations, UML diagram families and familiarity with modeling tools.

  • Practice Use Case and Class diagrams
  • Understand model, abstraction and UML notation
LAB 02

Software Development Models

Choose a development approach from scenario evidence and justify the choice.

  • Waterfall, Iterative, Prototyping, Scrum
  • Project-team formation and initial project idea
LAB 03

Domain Analysis

Move from an idea to an understood problem domain.

  • Problem statement and scope
  • Stakeholders and domain analysis
LAB 04

Requirements

Identify, classify and improve software requirements.

  • Functional vs non-functional
  • Write requirements for the group project
LAB 05

Use Case & Context Diagrams

Translate narratives into system boundaries, actors and system functionality.

  • Use Case diagrams
  • Context diagrams and scope
LAB 06

Class Diagrams

Represent the static domain structure and its relationships.

  • Associations and multiplicities
  • Generalization, aggregation and composition
LAB 07

Behavior Diagrams

Model interaction, workflow and object state from realistic narratives.

  • Sequence
  • Activity and State Machine
LAB 08

Behavior Modeling Assessment

Demonstrate behavioral-modeling competence through graded problems.

  • Sequence assessment
  • Activity and State assessment
LAB 09

Design Patterns & GRASP

Shift from correct notation to better responsibility assignment.

  • Singleton
  • Controller, Expert and Creator
LAB 10

Applying Patterns · Assessment

Select, apply and justify patterns in design scenarios.

  • Compare alternative responsibility assignments
  • Explain coupling/design improvements
LAB 11

Software Architecture

Organize systems at a higher level using packages, layers and architectural patterns.

  • N-tier, client–server, package diagrams
  • Pipe & Filter and MVC examples
LAB 12

Design Principles & Prototyping

Improve software structure and manage design complexity.

  • Decomposition, modularity and reuse
  • Information hiding and prototyping

Assessment model

What students actually produce

ModelsUse Case, Context, Class, Sequence, Activity, State and Package diagrams.
ReasoningProcess choice, design responsibility and pattern justification.
Project artifactsProblem/scope, requirements and selected project models refined through feedback.
Graded evidenceIndependent modeling/design problems that demonstrate skill rather than copying a worked example.
Recommended learning pattern

How each practical skill should appear in The Educator

Learn → Worked Example → Guided Practice → Independent Challenge → Project Transfer → Feedback. This keeps the useful scenarios from the source labs while removing the old separation between lecture knowledge, lab exercise and project work.

Important mapping finding: the historical labs contain strong UML and design practice, but testing practice is not represented as a comparable dedicated lab. The current Topic 12 and Mission 12 therefore fill a genuine practical gap rather than duplicating an old lab.
